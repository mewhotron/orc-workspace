# Provider-neutral model routing

The owner maps these task tiers to models available in their chosen host. No model name, API endpoint, provider or reasoning value is required by the core.

| Tier | Task characteristics |
| --- | --- |
| routine | Bounded, readily checked extraction, inventory or record updates |
| general | Scoped implementation, comparison and ordinary judgment |
| complex | Difficult diagnosis or interacting dependencies |
| architecture | Ambiguous design, consequential recovery or conflicting evidence |

Use the lowest tier likely to meet the acceptance criteria; do not force a cheap failure first. Default to general when unclear. Preserve mandatory domain consultation. Skip optional delegation when overhead outweighs useful work.

Keep mappings and spending preferences in local/preferences.md. An unset mapping means inherit the current host model and disclose unavailable controls. Validate actual supported model/effort options before dispatch. Never silently choose a more expensive provider, connect an account or launch paid benchmarks.

Record requested settings and runtime-confirmed settings separately. Make at most one automatic stronger attempt for an unresolved task, based on a failed check or concrete reasoning gap, within existing authorization and budget. Reconcile prior effects first. Permission, missing input and tool failures need their actual remedy, not a stronger model.

Measure only exposed usage telemetry and its scope. Missing usage is unavailable, never zero. This is a routing procedure, not a software-enforced spending cap or guarantee of lower cost.
